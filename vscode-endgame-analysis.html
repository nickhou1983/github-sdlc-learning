是建立发布信心。

SCOPE / 测试范围

Endgame 到底包含哪些测试？

Endgame 是面向候选版本的一轮集中质量验收，而不是一种单独的测试类型。它既包含测试活动，也包含缺陷处置、变更收敛和发布准备。

测试内容核心问题主要对象
新功能交叉测试不熟悉实现的人，能否正确理解和使用功能？本版本新增或明显变化的功能
缺陷修复验证原问题是否真的解决，有没有引入相邻问题？已关闭的 Bug、需要验证的改动
核心场景回归新版本是否破坏用户原本依赖的工作流？Golden Scenarios、重构影响区域
跨环境与兼容性换平台、配置、布局或旧数据后是否仍正常？桌面、Web、远程、扩展、历史状态
发布产物检查实际安装包能否安装、启动和基本使用？Stable RC、安装包、Server、CLI

与日常 CI 相比，Endgame 更强调真实使用情境和未知问题：CI 主要证明已有断言仍成立；Endgame 还要发现此前没有想到、没有编码成断言的问题。两者互补，不能互相替代。

官方测试观：不能机械执行指定流程、勾选完成后就结束。测试应当是探索性、开放式的过程。

依据：Endgame testing and verification；下文按不同质量目标重新归类，并非官方唯一分类法。

FEATURE VALIDATION / 新功能验收

以 Test Plan Item 组织交叉测试

TPI 是一份可以交给别人的测试任务

VS Code 使用带有 testplan-item 标签的 GitHub Issue，描述 Endgame 需要测试的功能。它不是泛泛的“把这个模块测一下”，而是有边界、可分配的任务。

组成典型内容目的
元信息 Header关联 Issue、平台、复杂度、作者、必要角色支持工具解析与任务分配
测试正文 Body功能背景、环境准备、步骤与相关说明让不熟悉实现的人独立测试

平台可指定 macOS、Windows、Linux，也包括 Web、WSL、SSH、Dev Container、iPad 或 anyOS。复杂度标记为 1–5；即使复杂度为 5，官方也要求控制在最多一至两小时，超出范围应拆成多个任务。

为什么不能只由作者自测？

TPI 应当按“测试者对该功能一无所知”的前提编写。通过 Authors 声明参与实现的人，分配工具可避免把测试分给作者；需要特定技能时，也可以预指定测试者或限定角色。

  • 摆脱实现者的预设：作者知道正确入口，用户不一定知道。
  • 暴露说明缺口：测试者看不懂步骤，可能意味着功能本身不易发现或理解。
  • 引入不同习惯：其他工程师、PM、设计师会走作者没有考虑过的路径。

真实案例：权限模式不是只测“选择器能切换”

microsoft/vscode#299339 将批准模式、用户设置、企业策略和错误处理组合起来测试：

场景测试重点
Default Approvals是否尊重已有设置；关闭全局自动批准后，是否重新请求确认。
Bypass Approvals是否跳过批准、遇错重试；提问工具是否仍等待用户回答。
Autopilot是否自动运行工具、回答问题并处理错误。
企业策略企业禁止全局自动批准时，相关高自主性模式是否不可用。

测试的是“模式 × 设置 × 策略 × 错误处理”的行为组合。权限工具栏和 Autopilot 自主执行还拆成不同 TPI，避免一个任务失去边界。

依据：Writing Test Plan Items。

EXPLORATION / 主动寻找反例

测试步骤是起点，不是边界

行为是否正确？

先检查功能是否按描述工作，再改变操作顺序、输入无效值、偏离推荐路径，观察它如何失败、恢复和解释错误。正确路径通过，并不能证明失败路径可控。

真实案例：Autopilot 的开放式测试

microsoft/vscode#299338 要求用较复杂的真实项目任务测试，并尝试无法完成的任务、请求中途断网、调整请求次数限制，观察 Agent 是否持续执行、是否过早退出。

这类测试关注完整执行过程及异常行为，无法只靠一个固定的成功用例证明正确。

设计是否合理？

官方要求测试者继续追问：设计是否说得通，能否简化，是否与 VS Code 一致，新用户能否理解和发现，会不会损害某种现有工作流。

“符合设计”不意味着“设计值得发布”。一个按需求实现、却让人困惑的功能，同样需要反馈。

是否存在相邻问题？

验证 Bug 时，要尝试原 Issue 之外的相似条件：其他入口是否有同类错误，修复是否只覆盖一种输入，其他配置下是否仍失败，是否破坏了另一条路径。

即使不确定某个现象是否算 Bug，也可以提 Issue。发现的问题不必局限于当前 TPI；陌生视角本身就是有价值的质量输入。

依据：Endgame testing and verification。

COVERAGE / 体验与开发者接口

UI、可访问性和 API 具体测什么？

UI：默认环境下好看，不等于真实环境中可用

维度检查内容典型风险
键盘操作不用鼠标能否导航、完成操作焦点丢失、控件无法触达
屏幕阅读器辅助技术下能否理解和操作可见但不可访问
缩放级别不同缩放下是否正常截断、重叠、布局失效
配色主题尤其检查高对比度主题文字不可见、状态难区分
尺寸与布局窗口、组件大小和工作台布局变化依赖固定宽度或默认位置
图标与 UI 设置更换图标主题、关闭相关界面元素依赖某个默认外观表达状态
命令与快捷键名称清楚、快捷键合理且不冲突难发现、与系统或产品快捷键冲突

API：不仅能调用，还要容易正确使用

面向扩展开发者的 API，也在 Endgame 验收范围内。重点包括：

  • 初学者是否有足够信息理解 API；JSDoc 是否清楚，链接能否在 IntelliSense 中正确呈现。
  • package.json 新配置的悬停文档、补全建议、代码片段是否正确；非法配置是否报错。
  • 命名是否与现有接口一致，有没有容易误用的隐含复杂度或陷阱。
  • 是否需要过多样板代码；示例扩展和文档是否更新，示例能否构建。
分析：API 发布后会带来长期兼容性负担。因此，易理解、易正确使用与运行结果正确，同样是质量的一部分。

依据：官方 UI 与 API 测试基础规范。

VERIFICATION / 修复闭环

“开发完成”与“验证通过”是两个状态

Endgame 会专门查询已关闭、但尚未验证的 Bug。关闭 Issue 代表提交了修复，不自动等于真实问题已经解决。

修复并关闭 Issue→ 他人依据步骤验证→ 通过 / 验证失败 / 补充步骤
标签作用
verification-needed明确请求验证。
verified用于验证流程；规范允许先加标签认领任务，避免重复验证。
verification-steps-needed步骤缺失或难以理解，无法验证；移除 verified。
verification-found验证时原问题仍存在；移除 verified。
标签解读注意：由于 verified 可能先用于认领，不应完全脱离 Issue 上下文，仅凭标签就断定验证已经完成。

优先验证自己报告、由别人修复的问题

原始报告者通常已经具备复现环境，了解触发条件和预期结果。这不是实现者自验，而是利用报告者的上下文降低验证成本。难复现问题还可以请求社区原作者验证。

晚期修复也必须有验证人

月更计划要求候选修复的 PR 作者寻找验证者，防止“原版本测过，但最后一天加的小修复没有实际验过”。越晚进入版本的变更，越不能依赖旧测试结论。

依据：Issue Tracking；microsoft/vscode#297011 · February 2026 Endgame。

REGRESSION / 保护已有工作流

验证用户已有的东西不会坏

Golden Scenarios：长期核心工作流

官方博客将 Golden Scenarios 定义为核心用户流程的预期行为描述。过去，团队在月度 Endgame 手工执行这些场景；转向周更时，开始交给 Agent 做合并后自动验证。

测试资产重点区别
Test Plan Item组织一次明确的测试任务可以是新功能探索，也可以针对重构区域检查
Golden Scenario保护核心用户流程的预期行为更适合长期复用，作为持续回归资产

二者可以关联，但不能等同。公开博客没有给出完整 Golden Scenarios 清单，也没有说全部场景都是合并前的硬门禁。

历史数据与版本组合：不能只测干净环境

真实案例：旧聊天会话升级后是否仍可恢复？

2026 年 2 月 Endgame 明确要求：安装新的 Stable VS Code 与 Stable Copilot Chat，验证旧会话仍能无错误显示，并且可以继续使用。

它检查的不是“新版本能新建聊天”，而是已有用户状态能否跨版本继续使用。

计划还包含 VS Code RC、Copilot Chat Stable、Codespaces Web 等组合验证，并提醒：如果核心 RC 因候选修复变化，可能需要在新构建上重新执行相关 Sanity 测试。

组件分别通过测试，不等于某个版本组合已经通过测试。构建变化后，也不能自动沿用旧构建的所有验证结论。

依据：How VS Code Builds with AI；microsoft/vscode#297011。

RELEASE SANITY / 最终交付检查

最后验收的是实际安装包

Release Sanity 与新功能深度测试不同。它确认用户实际下载到的候选产品可以安装、启动、基本使用，并覆盖 Server 与 CLI 等交付组件。

官方基础操作很朴素：安装并启动，打开文件或 About 对话框，点击侧边栏，执行命令，打开终端，安装并使用扩展。这些操作能暴露源码测试发现不了的打包或运行环境问题。

维度代表内容
WindowsSystem Installer、User Installer、Archive
macOS架构对应包、Universal 包
LinuxArchive、DEB、RPM、Snap
处理器架构x64、ARM64，以及适用的 ARM32
远程组件Server、CLI、不同 Linux 运行环境，包括 Alpine
连接链路CLI 启动 Tunnel，浏览器连接指定版本 Server

远程验证要求明确指定构建 commit，避免无意中测试到另一个版本。测试标识必须足够精确，才能把结果关联到最终交付物。

手工流程与自动化能力并存

Wiki 把 Sanity 描述为发布前的人工最终检查；而 1.111.0 仓库中已经存在自动化 Release Sanity 测试，包括不同平台、安装方式和签名检查能力。

覆盖边界：不能只根据旧 Wiki 判断它全部手工，也不能认定所有平台都完整自动化。当时自动化文档明确，macOS x64 只验证下载，不验证安装与运行。

依据：Sanity Check；1.111.0 Release Sanity 测试说明。

CHANGE CONTROL / 让验证结论保持有效

测完之后，不能再让版本失控

月更：先创造稳定的测试窗口

2026 年 2 月的实际计划安排了周一代码冻结、确保各平台构建正常；周二专门测试，除阻塞测试或构建问题外，避免提交修复。随后处理和验证缺陷，临近发布时提高修复审查要求，可延期的问题移出本版本。

分支之后，只允许经过讨论和批准的重要候选修复进入。这是在控制“移动靶”：如果被测构建一直变化，就很难把多人的测试结果累积为对同一版本的信心。

周更：压缩日程，并降低临时纳入功能的压力

转型早期的 1.112 Endgame 计划已经压缩为以下节奏：

时间安排
周一上午集中测试 TPI、验证 Bug
周一下午至周二修复必要问题，默认倾向将非必要问题延期
周二构建、内部发布及发布准备
周三讨论新增候选问题，启动发布
关键规则：若发现测试阻塞，建议把功能推迟到下一迭代。周更缩短了等待下次发布的时间，因此不必为了赶本次发布而冒险塞入未验证功能。

Endgame Champion 负责创建和跟进计划，协调测试人力、构建可用性、验证、候选修复、Sanity 与发布；并可根据缺陷、假期等调整日程。质量问题可以改变发布时间，而不是测试无条件服从原定日期。

依据：月更计划 microsoft/vscode#297011；周更早期计划 microsoft/vscode#300702；Running the Endgame。日程是具体版本实例，不是永久固定规则。

MARCH 2026 / 博客中的人机分工

哪些交给 Agent，哪些仍需要人？

以下状态描述以 2026 年 3 月博客发表时为准。博客描述了一种自定义验收 Agent：使用 Playwright MCP 启动 VS Code、导航到功能、操作并截图，评估结果是否符合预期；发现问题后在循环中继续修复，保留截图供人审查。10 月代码中已经可见的执行器与证据能力，在后续章节单独分析。

工作博客中的做法与状态
核心用户流程开始把 Golden Scenarios 交给 Agent 做合并后验证。
产品操作与截图已构建 Playwright MCP 驱动的自动验收能力。
发现问题后的修复可在 Agent 循环内修改并再次验证。
证据审查截图保存给人审查，不只依赖“已完成”的文字报告。
跨角色交叉测试工程师、PM、设计师继续参与，但压缩执行时间。
架构与体验取舍人继续判断，工程师对结果负责。
定性体验评分Taste-based grading 仍处于作者探索阶段。
演示录像、文档一致性自动生成录像和检查文档与产品体验的偏差，属于探索方向。

质量不能等于 Agent 的自我声明

“步骤执行成功”并不等于“测试充分”。官方 Endgame 要求测试者怀疑步骤是否遗漏重要情形；自动化验收同样需要明确预期、可审查证据和人工判断。

配套代码审查采用 Copilot Review 先行、工程师处理评论后再请求人工审查的工作方式。但它是整个质量体系的一部分，不应与 Endgame 测试混为同一种检查。

证据边界：公开文章未披露完整提示词、验收判定阈值、误判率或全部场景清单，也没有证明周更后的缺陷率下降。不能据此声称人工测试已被替代。

依据：How VS Code Builds with AI · Keeping Quality High as Velocity Increases。

CODE STUDY / UI 自动规划与自愈

Agent 规划，执行器运行，证据支撑判断

UI 自动验证不是让模型自由浏览后宣称“没有问题”，而是将规划、执行、判定与证据采集分层。外层 Agent 从 Issue 或 PR 提炼预期行为，生成可执行场景；底层测试框架负责启动产品、执行步骤并记录结果。

公开代码入口

入口文件职责
validate-ui-scenario/SKILL.md指导 Agent 从 Issue 编写场景、选择构建、运行并报告。
test/scenario/src/runScenario.ts定义场景接口，加载校验，逐步执行和结果处理。
test/scenario/src/application.ts选择实际产品、启动 VS Code、隔离用户环境。
test/scenario/src/evidence.ts采集截图、视频、Trace，生成清单与 HTML 报告。

自动规划：先明确可观察主张，再生成步骤

操作规范中的例子是：在设置中搜索 chat confirm，应当找到说明文字中包含相关信息的 Max Requests。Agent 需要把问题拆成环境、操作、预期和失败判据，而不是只生成点击序列。

规划工作为什么需要
基线检查先确认用 max requests 能找到目标设置，排除“构建中根本没有该设置”的原因。
界面机制分析设置列表是虚拟化的；需要滚动收集结果，不能因当前 DOM 没有目标就判定不存在。
独立验证信号根据结果文本、DOM、焦点或可访问性状态判断；操作返回成功不等于业务结果正确。
执行边界提前识别登录、硬件、主观判断或框架缺失的能力，并明确报告。

场景格式与执行链路

场景由 JavaScript 文件导出。下面是对接口的结构化简写，不是完整可运行脚本：

Scenario
  id, title                 场景身份
  source                    关联 Issue / TPI
  scenarioPath              可选的 Markdown 定义路径
  workspacePath             一次性测试工作区
  userSettings              初始化设置
  extraArgs, extraEnv       启动参数与环境
  stepPauseMs               录像中步骤停留时间
  steps[]
    id, title
    run(context)            执行操作与断言

context = { app, workbench, code, page, skip }

scenarioPath 用于记录关联定义；执行器实际加载的是 JavaScript 场景，不能说它已经实现了通用的 Markdown 自动解释执行。

Workbench 已封装 quickaccess、editors、settingsEditor、terminal、chat 等功能助手。场景优先使用这些助手，必要时再直接操作 Playwright Page。

Issue / 功能预期
  → Agent 编写 scenario.cjs
  → runScenario()
  → Workbench 助手 / Playwright Page
  → 真实 VS Code
  → 断言 + 截图 + Trace + 报告

版本与隔离：别在错误的产品上证明修复有效

运行目标用途
默认已安装 Insiders，否则 Stable复现已发布产品中的行为。
--dev验证当前源码中的未合并修改，必须保证构建输出已更新。
--build <path>针对明确的产品安装包运行。
--web --headless验证 Web 场景。

application.ts 准备隔离的用户数据和扩展目录，并拒绝通过额外参数覆盖隔离目录。这样可以减少用户真实设置、扩展和运行状态的干扰。用已安装产品运行成功，不能证明未合并代码已修复问题。

如何判定通过、失败与无法验证？

步骤行为执行器结果
run() 正常返回步骤记为 passed；返回文字写入报告。
抛出异常步骤失败，停止整个场景。
skip(reason, { needs })记录跳过，整个场景为 aborted，不算通过。
needs: human需要人完成，例如物理设备、主观判断或无法脚本化的登录。
needs: infrastructure理论上可自动化，但当前框架缺能力，应作为能力缺口报告。

失败后停止，避免在异常状态下继续操作并制造连带噪声。但执行器并不自动证明断言充分：如果步骤只点击、不检查结果，也可能正常返回。因此规范要求用独立信号验证，截图支持主张，不能单独建立正确性。

“自愈”属于外层 Agent，不属于 Playwright

外层 Agent：规划 → 编写场景 → 运行 → 分析失败
                                      ↓
                                  修改产品实现
                                      ↓
                                  重新构建、重跑

内部执行器：加载 → 逐步执行 → 留证 → 遇错停止

runScenario.ts 不调用模型修改产品代码。evidence.ts 中截图失败后的有限重试属于采集容错，不是代码自愈。博客中的修复循环，需要外层 Agent 读取结果并执行修改。

可信验证要求：有条件时先记录修复前的失败；不可为了得到通过结果而削弱断言；无法执行的步骤必须报告。修复产品与修复测试实现都可以，但不能修改预期来掩盖回归。

执行结果如何留下证据？

EvidenceService 输出逐步结果报告、manifest.json、步骤截图、原始录像、带说明的视频以及 Trace 和日志。完成阶段还会阻止将已失败步骤的运行标记为成功，并处理应用提前关闭等情况。

证据保存在 .build/vscode-playwright-mcp/evidence/<run-id>/。缺少 ffmpeg 或 ffprobe 时会警告并保留原始视频，不会因此停止场景；带说明的视频不是无条件产出。清单中的 commit 来自 CI 环境变量，也不能自动当作任意本地被测安装包的身份校验。

Skill 中的本地执行入口为：

npm --prefix test/scenario run compile
node test/scenario/out/runScenario.js <scenario.cjs> --dev

以上命令需要完整的 VS Code 源码构建环境；这里只展示公开入口，并未在本次分析中运行 VS Code 测试。

不可公开核实的部分：Skill 说明，PR 加上 ~requires-ui-validation 后，由 microsoft/vscode-engineering 研究改动、针对准确的合并候选运行场景并回贴结果。该仓库本次公开访问返回 404，内部规划提示词、修复次数上限及完整编排逻辑无法核实；不能据此编造实现。

关键代码：runScenario 执行循环；EvidenceService 完成与结果保护。

CODE STUDY / 黄金场景与持续回归

核心用户行为，如何变成可重复测试？

先区分三种不同资产

概念含义与用途
Golden Scenario核心用户工作流及其预期行为，定义必须保持的产品能力。
Golden Screenshot图片基线与视觉差异，用于检查外观；不是完整用户流程。
Smoke Test可重复执行的关键端到端测试，可作为持续回归实现。
公开证据边界：本次未在核实的公开入口找到博客那套完整 Golden Scenarios 目录。下述 Smoke 用例展示的是核心行为的实际代码化方式，不能宣称每个用例都与博客中的黄金场景逐一对应。

定义场景需要什么？

结合博客与公开接口，可将场景整理为：初始状态、操作路径、预期结果、环境条件、失败判据和证据。例如“编辑并保存后重启，内容仍存在”。这是工程分析提炼，不是一个已核实的官方统一 YAML Schema。

真实代码：文件保存、Hot Exit 与跨版本恢复

data-loss.test.ts 包含编辑器恢复、文件保存后恢复、未保存文件的 Hot Exit、自动保存，以及 Stable → Insiders 迁移等测试。

打开 app.js → 输入文本 → 检查 dirty 状态
  → 保存 → 检查 dirty 状态消失
  → 重启 VS Code → 断言文件仍包含输入内容

验证不是“保存命令没有报错”，而是重启后用户内容仍存在。对于跨版本恢复，用旧 Stable 创建状态，停止旧版本，再用同一测试用户数据目录启动新版本并验证。两个版本分别在干净目录启动，不能证明迁移兼容。

覆盖也有条件：没有可用旧版构建时，部分迁移测试会跳过；代码中还存在特定环境的隔离或跳过条件。测试文件存在不等于每次在所有环境都执行。

真实代码：搜索结果的确定性检查

search.test.ts 在测试工作区搜索 body，断言 6 results in 3 files；限定 *.js 后断言 4 results in 1 file；移除文件匹配后继续检查数量变化。

测试工作区由 test/smoke/src/main.ts 准备，默认来自 microsoft/vscode-smoketest-express。这里的可靠性来自可控输入、明确操作和结果断言，而不是模型主观评价“搜索看起来正常”。

一次性验证如何与长期回归分工？

validate-ui-scenario 规范明确：从 Issue 派生的一次性验证使用 Scenario；希望每次构建执行的确定性回归，应编写 Smoke Test。

新问题 / 新功能
  → Agent 编写一次性场景，快速复现并留证
  → 识别长期重要、可以稳定重复的行为
  → 实现为 Smoke 测试，纳入持续回归

这是由公开分工推导出的合理演进路径，不代表仓库已经存在自动把 Scenario 转成 Smoke 的转换流水线。

回归如何进入 CI？

当前 .github/workflows/pr.yml 包含变更影响检测、多平台测试、Electron Smoke 分片和统一的 PR Gate。汇总任务检查依赖任务结果，失败或取消等结果会使 Gate 失败，合理的选择性跳过允许通过。

不能混同两个时间点：博客提到的黄金场景 Agent 验证是合并后；当前 Smoke 工作流运行在 PR 阶段。工作流生成 Gate 检查，也不等于仅凭 YAML 就能证明分支保护禁止绕过。

本地 Smoke 入口示例：

npm run smoketest -- -g "Data Loss" --tracing
npm run smoketest-no-compile -- --build <产品路径> --tracing

关键依据：Smoke 测试操作规范；PR Gate 汇总代码。

CODE STUDY / Endgame 工程实现

结构化测试任务，加上版本级质量收敛

Endgame 没有一个覆盖全部过程的 endgame.test.ts。它由 Milestone、发布计划 Issue、TPI、验证标签、候选构建和 Sanity 流水线共同表达。

TPI 是可解析的 Markdown，而不只是文档

Refs: 关联 Issue

- [ ] windows
- [ ] linux

Complexity: 3
Authors: @作者
Roles: Developer

---

背景、环境准备、测试步骤与预期行为

配套公开仓库的 test-plan-item-validator/validator.ts 提供真实解析实现。parseTestPlanItem() 提取分隔线前的 Header、Issue 引用、平台名额、作者和角色；复杂度缺省为 3，范围必须为 1–5，并要求至少一个平台名额。

实现细节含义与边界
合并 Issue 创建者与 Authors保留作者集合，供分配工具避免作者自验。
勾选与测试人同时存在解析为完成状态需要同时有勾选和用户，不能只有一个孤立勾选。
通用平台名额归一化anyOS 等名额倾向归到当前名额较少的平台类别。
不等于完整人员调度器这段代码证明格式解析和平台名额处理，不能据此宣称已掌握随机人员分配或全团队负载均衡算法。

测试计划本身也被校验

TestPlanitemValidator.ts 根据配置，对错误 TPI 留下错误说明并切换无效标签；修好后清理错误状态；为关联 Issue 增加纳入测试计划的标签，并在可能时补充当前 Milestone。

对应的 单元测试 覆盖无效格式提示、重复运行不堆积评论、修正后恢复状态等行为。它保证计划可以被工具处理，但不能自动证明测试内容充分。

部署边界：这些代码证明配套仓库存在相关实现；本次未核实它目前在所有 VS Code 流程中的实际启用配置。

真实 TPI：同时检查应发生与不应发生的行为

Custom agent hooks · microsoft/vscode#299341

该测试任务 指定 Linux 与多个 anyOS 名额，复杂度为 3。测试者开启功能设置、创建自定义 Agent、配置 Hooks，检查提示与补全，并结合日志观察输入输出。

关键判据是：只有选中该 Agent 或通过 runSubagent 调用时 Hook 才触发，其他情况下不应触发。它是带负向约束的产品行为验证，而不仅是操作录像。

TPI 可以由人执行，也可以使用 Scenario 框架自动执行其中可自动化部分；公开证据不足以说明每个 TPI 都已经自动转为脚本。

如何发现漏测与晚期修复？

仓库中的 .vscode/notebooks/endgame.github-issues 是 GitHub 查询集合，而非产品测试程序。它汇总：

  • 当前 Milestone 仍开放的普通 Issue 和 PR。
  • 缺少验证步骤的问题，以及未完成的 TPI。
  • TPI 工具运行后新建并修复、但尚未验证的 Bug。

最后一项很关键：测试计划生成以后发生的新修复，不能从版本质量视野中消失。Notebook 把“纳入版本 → 纳入计划或单独验证 → 修复 → 补验”变成可查询的状态。

当前周更计划如何编排？

1.143.0 Endgame · microsoft/vscode#342482 展示了后续周更实践：开始前创建 TPI、补验证步骤与人力；将需验证的 Bug 分组生成 TPI；周一集中测试；只修复必要问题并倾向延期；包括晚期修复在内的改动都要验证；内部发布后再分阶段推送 Stable。

计划还链接 vscode-engineering 的 start-endgame.yml，记录自动创建的版本更新 PR 与 Notebook Milestone 更新 PR。这证明部分准备动作已自动化；内部工作流本身不可公开读取，不能进一步推测其全部实现。

最终候选构建如何进入 Sanity？

当前 product-sanity-tests.yml 使用 buildCommit 与 buildQuality 指定被测版本；公共 Sanity 模板 支持从流水线产物获取尚未通过更新服务分发的包，执行平台相关检查并输出测试结果、截图和崩溃诊断。

不是所有检查都是硬门禁：公共 Sanity 模板的 continueOnError 默认值是 true，调用方可以覆盖。测试存在不代表任何失败都会自动阻止发布，必须结合具体调用与审批判断。

三类实践的连接与边界

维度UI 场景验证黄金场景 / 持续回归Endgame
主要输入Issue、PR、功能预期核心用户流程规格本版本范围、TPI、待验证修复
主要目标证明某项改动符合预期保护核心能力持续成立判断整个版本是否适合交付
执行者Agent + Scenario RunnerAgent 或确定性 Smoke 测试跨角色人员与自动化工具
主要输出逐步结果与证据包回归结果、CI 状态已验证范围、剩余风险与发布决定
失败处置外层 Agent 修改后重跑调查失败、修复并回归控制候选修复、补验或延期

Agent 负责理解与规划，测试框架负责可靠执行和留证，Endgame 负责版本范围与发布风险。这三个职责相互连接，但不能混为一种“全自动测试”。

TAKEAWAYS / 可借鉴的质量机制

把测试组织成一条证据链

  • 有范围：每项重要变化对应明确的测试任务、环境和验证方式。
  • 有独立视角：交叉测试减少实现者盲点，步骤之外继续探索。
  • 有真实产品：既检查代码行为，也检查运行体验、旧数据和最终安装包。
  • 有反馈闭环：修复、失败、缺少步骤和延期均有可追踪状态。
  • 有变更边界：晚期修复受控，构建变化后重新判断验证是否仍有效。
  • 有最终责任：Agent 执行重复工作，人判断风险并对结果负责。

Endgame 真正管理的是：某项改动由谁在什么环境中验证，发现的问题如何处置，最后发布的构建是否仍对应这些验证结论。周更压缩的是等待和重复劳动，不应压缩这条证据链。
