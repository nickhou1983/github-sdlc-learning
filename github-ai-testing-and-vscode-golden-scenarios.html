STEP 01 / 变更识别

STEP 03 / 靶向功能回归

按变更影响面分层执行

建立“模块—接口—测试集—测试数据”映射，利用 Actions 路径/条件过滤实现 PR 级靶向验证，将全量回归放到夜间与发版前。

STEP 04 / 脚本兼容演进

低成本适配高频版本迭代

用 copilot-instructions.md 统一测试规范，抽离公共调用层与稳定定位符，让测试脚本随功能 PR 同步演进。

TWO-STAGE GENERATION · 先对齐测试场景矩阵，再生成可执行测试代码

避免“让 AI 直接写测试代码”的盲区：先出六维场景清单，再转自动化脚本

开发自测最容易犯的错误是直接根据刚写完的实现代码生成单元测试——如果代码逻辑写错了，生成的测试就会把 Bug 当成正确预期固化下来。

STAGE 1 · 六维自测场景矩阵（开发快速勾选确认）
测试维度 Copilot 辅助发散要点 推荐承载层级
01. 正常主链路 核心业务成功路径、标准入参与返回值校验 单元测试 + 核心 E2E 冒烟
02. 边界值条件 空值、零值、最大长度、分页临界、并发竞争 参数化单元测试（Table-driven）
03. 异常与容错 非法入参、下游超时、依赖服务报错、幂等重试 单元测试 + 契约/集成测试
04. 权限与多角色 未登录、越权访问、多租户隔离、只读角色拦截 API 集成测试
05. 状态流转 非预期顺序调用、重复提交、状态机回滚一致性 服务级集成测试
06. 数据与兼容 存量历史数据兼容、新旧字段默认值、事务完整性 数据库/接口集成测试

QUESTION 01.1 (PART B) // QUALITY GATES FOR TESTS 这些自测用例的质量如何保障？ FOLIO 05 / 12
FOUR-LAYER QUALITY ASSURANCE · 防止“无效测试”与“虚假覆盖率”

通过四道工程门禁，保障开发自测用例的有效性、准确性与可演进性

没有专职 QA 时，不能靠人工逐行抽检所有测试，必须把“测试用例本身的质量检查”固化到 PR 评审与 CI 流水线中。

01

需求可追踪性对齐

每一条验收标准（AC）都必须有对应的测试函数或自测勾选项支撑。

  • PR 描述中保留“验收项 ↔ 测试用例”映射清单。
  • 确保新增功能与修改逻辑不存在“无测试裸奔”分支。
GATE 1: AC TRACEABILITY
02

业务预期人工复核

重点审查测试里的 assert / expect 是否真正校验了业务结果。

  • 拒绝“只调用不校验返回值”的凑覆盖率测试。
  • 拒绝过度 Mock 导致只测了 Mock 本身的空壳测试。
GATE 2: ASSERTION VALIDITY
03

Copilot CR + CI 门禁

利用 Copilot Code Review 配合 GitHub Rulesets 强制拦截低质改动。

  • 配置审查指令：专项检查 PR 是否缺失异常/边界测试、是否存在脆弱断言。
  • Actions 强制要求增量代码测试通过方可合并。
GATE 3: AUTOMATED REVIEW & CI
04

漏测沉淀与变异测试

用线上/联调漏测反哺用例集，并对核心模块引入变异测试。

  • 每次修复 Bug 必须先补一个能复现该 Bug 的回归测试。
  • 对计费/权限等核心模块用变异测试检验断言检出率。
GATE 4: ESCAPED BUGS & MUTATION
CRITICAL INSIGHT · 覆盖率陷阱警示 高代码行覆盖率 ≠ 高质量测试。即使行覆盖率达到 90%，若断言缺失或未覆盖状态组合，依然会漏掉严重业务缺陷。衡量自测用例集质量的核心指标应当是：断言有效性、边界场景覆盖度、以及历史缺陷回归拦截率。

RISK-BASED TIERED EXECUTION · 按变更半径匹配测试范围与测试数据

用“三级分层执行 + 模块映射矩阵”替代高成本的每次全量测试

将测试资源集中在当前变更真正波及的模块与上下游链路上，让测试数据按标签按需初始化，兼顾反馈速度与拦截能力。

TIER 01 · 每次提交 / PR

靶向增量 + 核心冒烟

根据 PR 修改的文件路径与模块依赖，仅运行受影响模块的单元/接口测试 + 极少量核心主链路冒烟测试（5~10 分钟内完成）。使用轻量级内存数据或模块专属最小 Fixture。
TRIGGER: pull_request
DATA: IN-MEMORY / MINIMAL SEED
TIER 02 · 跨模块 / 公共变更

关联链路与契约测试

当 PR 触及公共库、鉴权中间件、数据库 Schema 或对外 API 契约时，自动升级触发上下游关联模块集成测试与接口契约校验，并按标签拉起对应业务域测试数据集。
TRIGGER: shared-path / label
DATA: DOMAIN-SCOPED FIXTURES
TIER 03 · 夜间定时 / 发版前

全量回归 + 黄金场景走查

通过 GitHub Actions schedule（每日夜间）及 Release 候选分支触发全量自动化套件、性能基线与端到端黄金测试场景，集中分析大规模测试数据与环境表现。
TRIGGER: schedule / release
DATA: FULL STAGING SNAPSHOT
ASSET MAPPING · 建立“四元映射表”

在仓库维护轻量级映射配置：代码目录 → 所属业务模块 → 关联测试 Tag（如 @order、@auth）→ 所需测试数据 Seed 脚本。PR 触发时只加载命中的 Tag 与对应测试数据，避免全量拉起无用数据。

ACTIONS PITFALL · 路径过滤与必过检查（Required Checks）陷阱

若在 Workflow 顶层使用 on.pull_request.paths 过滤，当某次 PR 未命中路径导致整个 Workflow 被跳过时，GitHub 分支保护的 Required Check 会一直处于 Pending 无法合并。正确做法：使用 paths-filter + Job 级 if 条件，并保留一个始终汇总结果的轻量 Gate Job。

固化 copilot-instructions.md

  • 在 .github/copilot-instructions.md（及目录级 *.instructions.md）中明确：测试框架版本、目录结构、Mock 规范、公共 Helper 与命名约定。

02 / 架构解耦与稳定标识

封装中间层，隔离变化点

  • UI 测试：禁用脆弱的 CSS 层级/XPath，强制使用稳定的语义角色或专属 data-testid，并封装 Page Object / Component Model。
  • 接口测试：抽离统一 API Client 与数据工厂（Factory），接口字段变更只需改一处封装层，无需逐个修改上百条用例。
ABSTRACTION: PAGE OBJECT & DATA-TESTID
03 / AI 辅助适配与同步门禁

随 PR 同改 + 故障自愈工作流

  • 同 PR 同步演进：将“功能代码改动必须同步更新对应测试脚本”纳入 PR DoD 与 CODEOWNERS 评审。
  • Copilot 辅助修复：将 PR Diff 与 Actions 失败堆栈一并交给 Copilot，快速定位是“功能真回归 Bug”还是“预期变更需更新脚本”。
CO-EVOLUTION: PR DOD & COPILOT FIX
# .github/copilot-instructions.md 测试规范片段示例 - 所有 E2E 测试必须优先使用 getByRole 或 getByTestId('xxx')，严禁使用动态样式类名。 - 接口请求必须通过 tests/helpers/apiClient.ts 调用，禁止在测试文件内硬编码 URL。 - 构造测试数据统一使用 tests/factories/ 下的 Builder 函数，测试结束必须清理状态。
FLAKY TEST GOVERNANCE · 不稳定测试隔离机制

快速迭代中最怕“偶发失败（Flaky Tests）”拖垮开发对自测的信任。应在 GitHub Actions 中统计重试与失败率，将非确定性失败脚本移入隔离观察区（Quarantine）专项修复，确保主干 PR 门禁保持高信噪比。

“黄金测试场景（Golden Test Scenarios）”
究竟是如何生成的？

很多团队误以为“黄金测试场景”是某个全自动生成的黑盒脚本库。事实上，在 VS Code 工程体系中，它是围绕真实高频用户目标精心设计、在真实环境中端到端走查、并通过 GitHub Issue 持续追踪演进的关键用户旅程（End-to-End User Journeys）。

PILLAR 01 · GOLDEN SCENARIOS

端到端关键用户旅程

以真实开发者或数据科学家的完整任务为纲（如 #283671 完成一场 Kaggle 竞赛），专门检验多组件协同与 AI Agent 交互中的“衔接裂缝”。

PILLAR 02 · TEST PLAN ITEMS (TPI)

迭代测试计划工作项

在每个发布周期 Endgame 阶段，针对新增/修改特性编写带 testplan-item 标签的 GitHub Issue（如 #158388），组织全员交叉探索测试。

PILLAR 03 · SMOKE TESTS

核心冒烟自动化套件

沉淀在 test/smoke/ 目录下基于 Playwright 的端到端自动化检查（搭配版本升级与热退出手工检查），守住每个构建包的基本盘。

1. 真实初始环境构建

2. 获取竞赛数据与安装依赖

3. 创建与编辑 Jupyter Notebook

4. 内核执行、报错诊断与迭代调优
运行单元格，当遇到缺包、维度不匹配或长耗时任务时，观察 Agent 诊断与修复表现。
5. 生成预测文件并完成竞赛提交
生成符合格式的提交文件并完成验证，检验端到端闭环是否顺畅。
FRICTION & DEFECTS EXPOSED · 沿途暴露的跨组件摩擦点（单测无法发现）

为什么所有单测都绿，用户端到端体验却可能不及格？

在 #283671 走查中，虽然最终任务能够跑通，但沿途暴露了大量跨模块衔接问题，并被拆分为独立子 Issue 追踪：

  • 工具调用与命令冗余：Agent 在操作 Notebook 与终端时出现不必要的命令切换或重复安装包。
  • 编辑定位与单元格偏移：模型修改特定 Notebook Cell 时偶发插错位置或覆盖上下文。
  • 长耗时单元执行状态感知：训练耗时较长时，Agent 等待策略与中断反馈不够清晰。
  • 环境与内核状态不同步：容器内新装依赖后，Notebook Kernel 感知与重启提示存在断点。

WHAT IT IS NOT · 常见误解（它不是什么）
  • 不是 VS Code 产品内置的某个“一键自动生成黄金测试”按钮或专有功能。
  • 不是单纯根据代码 AST 自动穷举出来的海量低价值单元测试。
  • 不是孤立验证某一个 API 参数或某一个 UI 弹窗的局部用例。
WHAT IT TRULY IS · 本质定义（它真正是什么）
  • 是工程团队围绕最高优用户价值提炼的代表性端到端业务剧本（Canonical User Journeys）。
  • 兼具功能验收、跨模块集成验证与 AI 交互摩擦度评估三重作用。
  • 以 GitHub Issue 为载体记录执行过程，并将发现的每个断点拆解为可闭环的缺陷单。
STEP 01 / 锚定真实用户目标

以“用户要完成什么事”立项

不按代码模块划分，而按核心用户画像的真实任务切入（例如：“数据科学家在容器里用 AI 跑完比赛”、“前端开发者从零脚手架到调试部署”）。优先挑选跨越多特性的主干路径。

STEP 02 / 固化环境与成功标准

定义六要素标准契约

每个黄金场景明确定义：① 用户角色、② 干净初始环境（如 Dev Container）、③ 起点前置条件、④ 关键阶段步骤、⑤ 阶段预期反应、⑥ 最终成功判据，确保不同成员走查标准一致。

STEP 03 / 实战走查与问题裂变

记录全过程摩擦并拆单

工程师在真实构建版本上完整跑通旅程，不仅看结果是否成功，更记录每一步的报错、卡顿、返工与困惑，在主场景 Issue 下关联派生出一个个具体的 Bug / Polish Issue。

三类机制各司其职：黄金场景抓端到端体验，TPI 抓当期新特性，Smoke 守底线回归

LAYER 01 · GOLDEN SCENARIOS

黄金测试场景（端到端旅程）

代表案例：microsoft/vscode#283671

  • 核心定位：验证跨组件、长链路、特别是含 AI Agent 协同的真实用户目标能否丝滑完成。
  • 生成方式：按核心用户画像提炼端到端剧本，在干净环境中实战走查并拆分摩擦点 Issue。
  • 解决痛点：专门发现“单点功能都正常，但拼在一起不好用或走不通”的系统性断层。

LAYER 02 · TEST PLAN ITEMS (TPI)

迭代测试计划项（testplan-item）

代表案例：microsoft/vscode#158388 & Wiki 规范

  • 核心定位：在每个版本发布前（Endgame 周），针对本期新增/改动特性进行团队交叉手工探索验证。
  • 标准结构：Issue 顶部包含元数据头（关联特性、复杂度、支持平台 anyOS、勾选框），正文面向未参与该功能开发的其他工程师写清前置配置与测试要点。
  • 解决痛点：打破“写代码的人自己测自己的盲区”，无需专职 QA 即可实现高质量内部互测。
FOCUS: NEW FEATURE CROSS-TEAM VERIFICATION
LAYER 03 · SMOKE TESTS

冒烟测试套件（test/smoke/）

技术栈：Playwright 自动化 + 关键手工检查

  • 核心定位：快速验证构建产物在 Web / Electron 各端的核心基础能力是否可用。
  • 执行机制：按功能域分片（Terminal、Task、Debug、Localization 等）自动化运行，支持针对特定 Feature 单独跑对应套件；辅以版本升级（Upgrades）与热退出（Hot Exit）手工验证。
  • 解决痛点：以极低耗时守住每次打包发版的基础可用性底线。

固化进 Actions 与指令库

将黄金场景中稳定的主干步骤转化为 Playwright / API 冒烟脚本，结合 copilot-instructions.md 与路径分级触发，实现低成本长期演进。
